# Valhalla menu site

Menu and WhatsApp ordering site for Valhalla, a chimney cake cafe in Egypt. Rebuild, because the previous developer never handed over the source. Owner is non-technical and must be able to run the content himself.

`PROMPT.md` is the original brief. This file holds the decisions that outlive it. Where they disagree, this file wins.

## Data

- Supabase is the source of truth. `menu.json` is the seed and the rollback, nothing more.
- Never hardcode a price, an item name, or a category name into a component. If a string would change when the owner changes it, it comes from the database.
- Expected row counts after seeding: 15 categories, 134 menu_items (118 flat price, 16 sized), 32 item_sizes. If a change moves these, say so out loud.
- Seeds are idempotent and must not clobber prices the owner has edited since the last run.

## Availability

`is_available = false` renders the card **dimmed with the add control disabled**, not hidden. This is how the cafe marks something sold out mid-shift. Consequences that follow from it and must not be undone:

- Anonymous select on `menu_items` and `item_sizes` is **not** gated on `is_available`. The front end decides presentation, the database does not filter it away.
- Only `categories` is gated, on `is_active`.
- Disabled means `aria-disabled`, not keyboard reachable, not clickable through the dimming. Greying it visually is not enough.

## Cart

- localStorage holds item id, size label, selected addon option ids and quantity only. Never prices, never names, for the item, the size, or an addon. All of it is resolved from server data at render.
- A cart that has sat in a browser for weeks must never send an order at weeks-old prices. This is the single most damaging bug this project can ship. That now covers addon surcharges too, not just the base/size price.
- Version the storage key so a shape change invalidates old carts instead of crashing on them. `valhalla-cart-v2` (2026-07-31) added addon option ids; a v1 cart is simply not read back rather than guessed at.
- A restored cart referencing a deleted or unavailable item, a size that no longer exists, or an addon option that's been deleted or gone unavailable drops that line and tells the user what was removed.
- A cart line's identity is item + size + addon selection, not just item + size. The same drink with different extras is two lines, not one line with a bumped quantity.

## Item add-ons

Optional, per-item extras with their own surcharge ("Extra Sauce", "Extra Flavor", "Extra Boba Topping" on the old site, e.g. Ice White Mocha's sauce options at +30 EGP each). `item_addon_groups` belongs to a `menu_items` row; `item_addon_options` belongs to a group. A group is optional or required and single- or multi-select (`is_required`, `allows_multiple`), per group, not hardcoded, though every group seeded so far is optional and multi-select. Same `is_available` "dim, don't hide" rule as everywhere else, at the option level.

This is a different shape from the custom-build schema (`supabase/migrations/20260728164633_custom_build_schema.sql`): custom builds are a standalone product built from scratch (no base item, every step required in v1). Item add-ons bolt optional extras onto an *existing* catalog item. Don't conflate the two or try to merge their tables later, they answer different questions.

The custom-build migration's own header still says "DRAFT, NOT YET APPLIED... do not run db push until signed off", and per "never edit an applied migration" that comment is not getting touched now that it's wrong, but it *is* wrong: `supabase db push` batches every locally-pending migration into one prompt, so approving the 2026-07-31 item-addons push on 2026-07-31 also applied this one, nobody separately signed off on it. Tables exist live (`custom_builds`, `custom_build_steps`, `custom_build_options`), empty, RLS clean per `get_advisors`, no application code reads them, so nothing user-facing changed. But the actual cone-builder feature (UI, data, the "raised with the owner, not built" scope note in `get-menu.ts`) is still entirely unbuilt. Don't read the schema existing as the feature being greenlit.

Data entry for add-on groups/options happens through the dashboard, same as everything else, not through a script. One real example (Ice White Mocha) was seeded once from a screenshot to prove the feature end to end; its "Extra Boba Topping" group is known-incomplete (the screenshot cut off after one option), don't treat it as the full list.

## Security

- `service_role` key never appears in a client component, in any `NEXT_PUBLIC_` variable, or in the repo. `.env.local` only, gitignored, with a committed `.env.example` holding empty values.
- Anonymous role has select and nothing else. No anonymous insert, update or delete anywhere, including storage, and no `orders` RLS policy either, that table grants anon nothing at all, not even select (see Admin dashboard, Orders). A customer's browser can *trigger* an order write via one server action, but the browser itself never holds a client capable of writing to any table, RLS is unchanged and unweakened by that feature.
- The `menu-images` bucket is public read via its `public` flag. Do not add a `storage.objects` select policy back, it re-enables bucket listing.
- Writes happen through the dashboard under the owner's own login, or through `service_role`-only RPCs.
- Run `get_advisors` for security and performance after any schema change and fix findings before moving on.

## Migrations

- Never edit an applied migration. Fix forward with a new one.
- RLS goes in the same migration as the table it protects.
- The price-or-sizes rule is enforced by deferred constraint triggers, not a CHECK, because it spans two tables. Converting an item between flat price and sized needs both statements in one transaction.

**No auth yet, by design, and the whole structure exists to make adding it a one-file change.** Every admin route lives under `admin/app/admin`, one layout (`admin/app/admin/layout.tsx`), one function in it: `isAdminRequestAuthorized()`, currently a stubbed `return true` with a `TODO(auth, later session)` comment. That's the only call site. Wiring up real auth later means replacing that one function's body, nothing else under `admin/app/admin` needs to change or know how auth works. Do not add a second guard anywhere else, do not check auth per-route, everything funnels through this one function. **This matters more now than it did when admin was a route on this project**: back then, safety came from `SUPABASE_SERVICE_ROLE_KEY` never being set on *this* project's Vercel deployment. That specific safety net stopped being true 2026-08-01 when order recording needed the key on this project too (see the Orders entry below) — it's set here now, deliberately, scoped to one server action that only ever inserts a validated row, not a reopening of the admin question. Once `admin/` is ever actually deployed as its own project, that safety net doesn't automatically carry over, whoever deploys it will need to either set up Vercel Password Protection on that new project or replace the auth stub first. Don't deploy `admin/` with its service-role key set and this stub still returning `true`.

**No new anonymous write path on the customer-facing site, verified, not just intended.** Every admin mutation goes through a Next server action (`admin/app/admin/products/actions.ts`) using a `service_role` client (`admin/lib/supabase/admin.ts`), never a client-side Supabase call. No migration was touched building any of this (`git status supabase/` confirms it), so RLS on the live database is exactly what it was: anon gets select only, everywhere, still zero anonymous insert/update/delete policies on any table. `SUPABASE_SERVICE_ROLE_KEY` is still deliberately absent from this project's Vercel environment variables (see the pre-launch deploy-blockers pass) — that remains true and remains the reason this project's own deployment has no live write path, independent of whether `admin/` ever gets hosted elsewhere.

**Products page**, everything through server actions in `admin/app/admin/products/actions.ts`:
- List, grouped by category, via the service_role client (`admin/lib/admin/get-admin-menu.ts`'s `getAdminMenu()`, shared with the Stats tab, deliberately separate from the customer project's `lib/menu/get-menu.ts` anon-gated, cached `getMenu()`, since admin needs to see inactive categories and unavailable items unfiltered, not just what a customer would).
- Edit name, description, price, availability, popular, inline per row, no modal (`ProductRow.tsx`).
- A sized item's individual size prices are editable (`item_sizes.price`, bulk `upsert`), but sizes can't be added, removed, or relabeled, and an item can't be converted between flat-price and sized. That conversion needs both statements in one transaction (see Migrations above); scoping it out rather than building it half-safe.
- Photo replace runs the exact same resize-and-convert-to-WebP step as `scripts/upload-images.ts` (1600px max width, quality 82) server-side in the action, so an owner-uploaded photo never lands in storage as a raw file regardless of what they picked. This closes the exact gap the pre-launch pass flagged and left open ("an owner-driven image replacement can bypass the pipeline"). Overwrites the item's existing storage path when it has one (`image_url` never changes on a replace), generates a fresh one from category-slug/item-slug when it doesn't, same convention the seed pipeline uses.
- Delete has a confirm step, cascades through `item_sizes`/`item_addon_groups`/`item_addon_options` automatically (all `on delete cascade` from `menu_items`, see `20260727194235_menu_schema.sql`), no orphaned rows.
- Create is flat-price only, deliberately: a new sized item needs its `item_sizes` rows created in the same transaction as the `menu_items` row (the deferred constraint trigger again), which a single `supabase-js` insert can't do. The seed pipeline already solved this once with a PL/pgSQL RPC (`admin_upsert_menu_item`), but it's upsert-shaped for idempotent seeding, not create semantics, a duplicate name silently returns the existing item instead of erroring, wrong UX for an interactive "create" button. Sized-item creation needs its own real form later, not this RPC bolted on.
- Every mutation calls `revalidatePath("/admin/products")` **and** `router.refresh()` on success. Caught 2026-08-01 from a real bug report (toggling an item unavailable then back did nothing the second time): `revalidatePath` inside the action invalidates the server cache, but a server action called directly from a button's `onClick` (not a native `<form action>` submit) doesn't reliably push fresh props back into an already-mounted client component on its own. Without the explicit refresh, a second toggle computes `!item.is_available` against the same stale prop the first toggle read, so both clicks send the same value. The underlying data was never actually corrupted, only the on-screen state; verified directly against the real database before concluding that. Every mutation handler in `ProductRow.tsx`/`NewItemForm.tsx` calls `router.refresh()` on success now, not just some of them.

All end-to-end verified directly against the real database before being called done (create, edit, both toggles, photo upload with a real `sharp` conversion, delete with storage cleanup), not just "the page renders."

**Stats page (`admin/app/admin/stats/page.tsx`): every number on it is computed live from `getAdminMenu()`. None of it is invented, and one card says so explicitly.** Item/category counts, available-vs-sold-out, popular count, items per category, flat-price average/min/max, sized-item count, photo/add-on/rating coverage, average of items that actually have a rating. Revenue is deliberately not a number: no order is ever persisted anywhere (see Orders below), so there is nothing real to compute it from. Don't let a future pass quietly wire this up to a fabricated number to make the card look complete.

**Orders are real now (2026-08-01, direct follow-up request the same day it was deferred).** A row is written the moment a customer taps "Order on WhatsApp" on the checkout step (see the two-step checkout entry below), by `lib/orders/create-order.ts`, a `"use server"` action on the *customer-facing* project, not admin. This is the first anonymous write path this project has ever had. It does not gate the actual order: the `wa.me` link still opens regardless of whether the database write succeeds, the row is a courtesy record for the owner alongside it, not a precondition. If the write fails, the WhatsApp link still opens and the real order still goes through, see `CartDrawer.tsx`'s own comment for why the failure is swallowed rather than shown to the customer.

**Checkout is select items -> cart -> checkout -> WhatsApp now, not cart -> WhatsApp directly (2026-08-01, same-day follow-up clarifying the original Orders request).** `CartDrawer.tsx` is a two-step drawer/sheet (`step: "cart" | "checkout"`, one shared shell, no separate route, same reasoning as the item-detail overlay for staying an in-place panel rather than a page navigation for a transient interaction): the cart step is unchanged (quantities, removal, running total, a "Checkout" button where "Order on WhatsApp" used to be); the checkout step adds a read-only order summary and two required fields, name and phone number, with "Order on WhatsApp" only enabling once both are filled (name non-empty, phone at least 8 digits after stripping non-digit characters, `isValidPhone` in `CartDrawer.tsx`). Reopening the drawer always lands back on the cart step, not mid-checkout, a stray tap days later shouldn't resume an old form.

`lib/cart/whatsapp.ts`'s `buildWhatsAppOrder` now takes `customerName`/`customerPhone` as required params and includes them as `Name:`/`Phone:` lines in the message text, both server-side (`create-order.ts`, for the stored record) and client-side (`CartDrawer.tsx`, for the actual `wa.me` link, computed live via `useMemo` off the live form state so the link is always current as the customer types, not just at submit). Because the WhatsApp URL now depends on values only known at checkout time, `use-cart.ts` no longer computes `whatsappUrl`/`whatsappMessage`/`whatsappTruncated` at all, that responsibility moved entirely into `CartDrawer.tsx`; nothing else consumed those fields (checked directly, `useCartContext()`'s other callers only use `addItem`).

`orders.customer_name`/`customer_phone` (`supabase/migrations/20260801170000_orders_customer_contact.sql`) are nullable at the DB level, not `NOT NULL`, on purpose: a real order was placed live through the original two-field-free flow before this migration existed (checked before writing it, one real row, not a test artifact) and it honestly has neither, backfilling it with an invented value would be the exact "never invent business data" violation this project refuses everywhere else (see Content). "Required" is enforced one layer up instead, `create-order.ts` rejects an empty name or empty phone before the row is ever written, so every order from this point forward has both, without the database lying about the one row that predates the field. `admin/app/admin/orders/OrderCard.tsx` shows `customer_name`/`customer_phone` under the status row, with an explicit "placed before checkout collected these" note for that one legacy row rather than silently rendering nothing.

Schema (`supabase/migrations/20260801160000_orders_schema.sql`): `orders` (`id`, `created_at`, `status` — `new`/`confirmed`/`completed`/`cancelled`, no automation, an owner action in admin moves it forward — `items` jsonb, `total_price`, `whatsapp_message`). `items` is a deliberate snapshot, not a live reference: unlike the cart (which must always resolve current prices because localStorage could be weeks stale, see Cart above), an order row is a historical record of what was actually quoted at that moment, a later price change must not silently rewrite it. RLS is enabled with **zero policies for anon, not even select** (every other table in this project at least grants anon select, this one grants nothing) — the browser is never given a Supabase client capable of touching this table at all, every access goes through a service-role client, either `create-order.ts` to write or `admin/`'s `get-admin-orders.ts` to read. Verified directly: an anon-keyed client's `select` on `orders` returns empty (not an error, RLS silently filtering), its `insert` is rejected outright ("new row violates row-level security policy").

`create-order.ts` never trusts a client-supplied name, price, or total, same discipline as the cart's own "never trust a stored price" rule (see Cart), applied a second time so a manipulated request can't write a fabricated cheap order into the record. It takes only the raw cart identity (item id, size label, addon option ids, quantity) and re-resolves it server-side against a fresh `getMenu()` read, reusing `resolveCartLines`/`buildWhatsAppOrder` verbatim (the exact functions the client used to build the on-screen cart and the WhatsApp text) rather than duplicating that logic. No rate limiting or abuse prevention beyond that: someone could still script real (not fake-priced) orders repeatedly, that risk was accepted as proportionate for this traffic level rather than built out unprompted, revisit if it's ever actually a problem.

Scoped the same way admin's own copy of this pattern already is: `"use server"` boundary keeps the key out of the client bundle, same guarantee already relied on for the anon client.

`admin/app/admin/orders/page.tsx` lists real orders now (same 30s ISR window as Products/Stats, `setOrderStatus` in its own `actions.ts` revalidates on write), status changeable per-order via a `<select>` in `OrderCard.tsx`. Don't let a future pass fold it into the plain KPI grid on a hunch, that was a deliberate call, not an oversight, revisit only if the reasoning above no longer holds.

**Products and Stats carry a 30s ISR window now, not `force-dynamic` (2026-08-01).** Caught from a real report that switching tabs felt slow: every navigation was re-running `getAdminMenu()`'s full nested query live, with zero caching, because both the pages AND `admin/app/admin/layout.tsx` itself were marked `force-dynamic`. That layout's own `force-dynamic` was the one actually blocking the fix at first: a dynamic layout forces its whole subtree dynamic regardless of what an individual page exports, so simply adding `revalidate = 30` to the page files alone did nothing until the layout's own directive was removed too, caught by checking `next build`'s route markers (`ƒ` vs `●`) after the first attempt silently didn't change anything. `getAdminMenu()` is wrapped in React's `cache()` now too, matching the customer site's own `getMenu()`. Every mutation in `products/actions.ts` already calls `revalidatePath` on both `/admin/products` and `/admin/stats` (added the Stats path at the same time, it reads the same underlying data and needs the same immediate invalidation), so a save/toggle/delete is reflected immediately regardless of the window; 30s only bounds staleness between page loads with no write in between. Measured: repeat navigation to Products went from ~1s (a live query every time) to ~11ms (served from cache). The Stats page's "Updated just now" label was changed to "Live within 30s" since the old wording stopped being accurate once this shipped. `AdminNav.tsx` and `AdminSidebar.tsx`'s `Link`s also now set `prefetch={true}`: default "auto" prefetch only warms the shell for a route that isn't fully static, not the actual data-bearing payload, same fix and same reasoning as the customer site's `MenuItemCard.tsx` Link (see the item-detail-lag entry earlier in this file). This doesn't extend the "must stay dynamic" rule that section documents to admin, that rule is specifically about the customer site's `@modal` interception on Vercel, a completely different mechanism admin doesn't have.

**Stats is the landing page now, not Products (2026-08-01, explicit request).** Both root redirects (`admin/app/page.tsx` for the bare domain, `admin/app/admin/page.tsx` for `/admin` itself) point at `/admin/stats`; both were `/admin/products`. `AdminNav.tsx`'s `TABS` and `AdminSidebar.tsx`'s `NAV_ITEMS` arrays were reordered to match (Stats first) rather than leaving the landing page disagree with the nav's own reading order. **Products redesigned as a card grid, not a dense row list (2026-08-01, explicit request).** `ProductRow.tsx` renamed to `ProductCard.tsx` (a real rename, not cosmetic: the shape actually changed from one row in a bordered list to one card in a responsive grid, `ProductsClient.tsx`'s container went from a single `--border-default` list box per category to `grid-cols-2 sm:grid-cols-3 lg:grid-cols-4 xl:grid-cols-5`). Now split into two distinct controls on a full `aspect-square` card-top image: clicking the photo itself opens a full-size lightbox (plain `<img>` inside a `fixed inset-0` overlay, sized off the photo's own natural dimensions via `max-h`/`max-w`, not `next/image`, which needs a known size upfront and this modal deliberately doesn't have one; closes on backdrop click, an `X` button, or Escape), while a small always-visible camera badge in the photo's bottom-right corner is the *only* upload affordance (covers both "add a first photo" and "replace the existing one", one control, not two). Popular/Sold-out badges now sit on the photo itself too, top-left/top-right, mirroring the customer-facing `MenuItemCard.tsx`'s own badge placement, so scanning the grid for problems (something sold out, something worth double-checking) doesn't require reading the toggles below every single card. **Admin writes now reach the live customer site immediately, not just within its 60s ISR window (2026-08-01, explicit request: "make sure when i change the image it change dynamic to the customer").** Real gap, not a hypothetical: once `admin/` became its own Vercel deployment (see above), every `revalidatePath` call in `products/actions.ts` only ever cleared *admin's own* Next.js cache, never the customer-facing site's, because they're separate deployments with separate caches. The database write itself was always correct and immediate (CLAUDE.md's actual hard requirement, never serving a stale *price*, was never at risk, since every page still reads live from Supabase on cache miss), but a photo/name/price/availability edit could sit un-reflected on the customer site for up to `app/(customer)/page.tsx`'s own `revalidate = 60` window. Fixed with on-demand revalidation across the deployment boundary: the main project gained `app/api/revalidate/route.ts`, a POST handler gated on a shared secret header (`x-revalidate-secret`, checked against `REVALIDATE_SECRET`) that calls `revalidatePath("/")` and `revalidatePath("/item/[id]", "page")`. `products/actions.ts`'s `revalidate()` helper now awaits a new `revalidateCustomerSite()` after its two existing local `revalidatePath` calls, which `fetch`es that route using two new admin-only env vars, `CUSTOMER_SITE_URL` and `REVALIDATE_SECRET` (the secret's value must match across both projects, everything else about the two projects' env stays independent). Deliberately best-effort: wrapped in try/catch with a 4s `AbortController` timeout, failures are swallowed rather than surfaced to the owner as a save error, because the database write already succeeded before this runs and the 60s ISR window is still the fallback if the customer site is briefly unreachable, this mechanism only ever affects *how fast* a change becomes visible, never *whether* it's correct. Verified for real: toggled a real item's name via the service-role client the same way `actions.ts` does, confirmed the live customer site kept serving the old cached name until `/api/revalidate` was called, confirmed it flipped to the new name immediately after, then reverted the name and revalidated again so nothing test-shaped was left live.
